# Mobbin 设计调研

用官方 Mobbin MCP 插件搜索真实产品界面，看图提取设计模式，产出可溯源、可直接打开的 HTML 设计 Spec。适用于"某个组件该怎么设计"的调研，不用于一般 UI 开发。

## 工作流

1. 澄清组件 → 2. 规划查询词与竞品名单 → 3. 搜索与钻取 → 4. 看图提取 → 5. 提炼模式 → 6. 产出 HTML Spec → 7. 审阅闭环

每步都有完成标准；未达标不得进入下一步。执行前先读 [`references/workflow-guide.md`](references/workflow-guide.md) 获取各步的判断细则，需要命令参数或脚本用法时再读 [`references/capabilities.md`](references/capabilities.md)。

## 1. 澄清组件

用交互接口（见"交互接口"节）向用户拿三要素：

- **组件/页面**：研究什么（登录页、设置页、onboarding、结账流程……）
- **平台**：iOS 还是 Web（官方只有这两档）
- **目标**：找布局参考 / 学交互细节 / 对比竞品风格

用户说不清时：先用组件名做一轮试探搜索，拿真实结果回问帮用户聚焦，不要干等。

**完成标准**：能一句话复述"{平台}的{组件}，目标是{目标}"，用户已确认。

## 2. 规划查询词与竞品名单

查询词采用"组件名 + 按需限定词"（如 `settings preferences`、`dashboard analytics`），一个组件规划 1 个主查询词，需要时加限定词，一次只问一件事。钻取指定 App 时在描述前加 App 名（`Notion settings screen with toggles`）。

按需规划竞品名单：根据组件类型与平台推断 3-7 个典型 App（直接/间接/标杆/替代的分类思维只用于选 App，不做重表格），产出"App 名 + 一句选择理由"的轻量清单，用交互接口让用户按需增删。

**完成标准**：每个查询词都能让不熟悉上下文的人明白"找什么界面、含哪些元素、属于哪个 App（如有）"；竞品名单（如有）已获用户确认。

## 3. 搜索与钻取

按目标选择命令（参数细节见 `references/capabilities.md`）：

- 单张界面 → `search_screens`（默认 deep 模式；换角度搜索时用 `exclude_screen_ids` 去重）
- 多步流程 → `search_flows`（返回按 position 排序的每屏预览）
- 网站区块 → `search_sections`

轮次策略：先全局搜一轮建立候选集 → 对 2-4 个代表性 App 各钻取一轮（查询词加 App 名）→ 不足时换角度（换元素词/平台/模式）再搜。每轮记录"搜索词 + 链接"作证据链。

**完成标准**：候选集覆盖"全局 ≥3 个不同 App"，或"目标 App ≥3 张屏 / ≥1 条流程"，且每项有链接可溯源。

## 4. 看图提取

逐张查看返回的图片本身，禁止只凭元数据（app_name、标题）下结论。每张屏快速过一遍记录布局与风格亮点；对 3-5 张重点屏做四维深挖（布局/视觉层级/交互/导航）。

先用预览图筛选重点屏，确认有价值后取完整大图与主色板：

```bash
python3 scripts/fetch_screen_image.py https://mobbin.com/screens/<id> --out screens/
python3 scripts/extract_palette.py screens/<id>.png --top 6
```

**完成标准**：每张纳入分析的屏幕有"布局/层级/交互/导航"四维描述，重点屏附带大图与主色板证据。

## 5. 提炼模式

把观察跨 App 归纳，不罗列截图：每维度（布局/层级/交互/导航）提炼**共性**（多数 App 的做法）、**差异**（分叉点）、**例外**（亮点或坑）。每条模式注明来源 App 与链接。

**完成标准**：每个维度至少 1 条共性或 1 组差异，且每条可溯源。

## 6. 产出 HTML Spec

复制 [`assets/spec-components.html`](assets/spec-components.html) 的 token 与所需组件片段，替换占位符生成单文件 HTML，存调研输出目录。图片本地化，用户 `file://` 直接打开即可审阅。结构：标题区（组件+平台+日期+目标）→ 图片收集 → 设计模式 → 建议（可选）。布局用组件自由组合，不要整体重写样式。

图片收集分两层：**重点图卡**（深挖屏幕，大图 + 四维分析 + 主色板，Mobbin 链接悬浮在图片上）+ **参考墙**（模式引用过的其余屏幕，缩略图，点击全屏查看）。**所有被模式卡引用的来源 App，必须能在图片收集中找到对应图片**。

**完成标准**：用户打开 HTML 后无需再打开 Mobbin 就能看到完整证据、分析与结论；每张重点图卡可 hover 出 Mobbin 链接；每条模式卡引用的来源 App 都在图片收集中有对应图；**HTML 引用的所有图片文件都已复制到输出目录**（打开页面后逐一核对无裂图）。

## 7. 审阅闭环

将 HTML Spec 交给用户确认。用户提修改意见时回到对应步骤迭代（改查询词/补图/重提模式），直到确认。用户明确要求实现时才进入实现环节（按模式建议改造目标组件），否则停在审阅。

**完成标准**：用户确认 Spec，或明确要求修改并已迭代。

## 交互接口

澄清组件、确认竞品名单等需要用户输入时：Codex 环境用 `request_user_input`（1-3 个互斥选项，推荐项前置标注 Recommended）；Claude 环境用 `ask user question`。接口不可用时降级为直接在对话中提问。

## 资源

### scripts/

- `fetch_screen_image.py`：从屏幕 ID/URL 下载完整大图（步骤 4 用）
- `extract_palette.py`：从图片提取主色板（步骤 4 用）

### references/

- `capabilities.md`：3 命令参数与返回结构、按 App 钻取/完整大图/主色板等变通能力、脚本用法——需要命令细节或确认能力边界时读
- `workflow-guide.md`：各步判断细则（查询词构造、轮次策略、四维分析、Spec 结构）——执行前通读

### assets/

- `spec-components.html`：设计 token + 原子组件库（证据卡/色板/模式卡/流程步骤条），生成 HTML Spec 时复制使用
