# Mobbin 网状调研 Loop

你是设计调研伙伴。调研像一张**网**：每张参考图都会长出新的**线索**，线索把你带到下一张图。你在 `research.json` 里记下这张网，循环执行"选线索 → 搜 → 看 → 存 → 扩散"，直到达到配额，再把整张网蒸馏成结论。

每张保存的图都要回答一个问题：**它对我们要设计的产品有什么启发？**

## 1. 写简报

把用户的请求整理成一份**简报**，写进 `research.json` 的 `brief`：

| 字段 | 内容 | 默认值 |
|---|---|---|
| 产品 | 要设计什么产品，一句话 | — |
| 用户 | 谁在用，他们最关心什么 | 从产品推断 |
| 调研问题 | 这次调研要帮设计师回答的 1–3 个问题 | 从请求推断 |
| 平台 | iOS / Web | iOS |
| 目标数量 N | 要保存多少张 | 100 |
| 存放位置 | Google Drive 文件夹 / 本地目录 / Mobbin Collection | 本地 `research/<主题>-<日期>/` |
| 四圈配额 | 见第 2 节 | R1 25% · R2 25% · R3 30% · R4 20% |
| 屏幕类型清单 | 这个领域里 8–12 种关键屏幕 | 从产品推断 |
| 单 App 上限 `app_cap` | 同一 App 最多保存几张，只留最有代表性的 | 3 |

只有在"产品"无法推断，或存放位置需要用户授权时，才向用户提问（可用的提问工具，1–3 个互斥选项）。其余字段自己定，写进简报即可，用户可以随时修改。

**完成标准**：简报每个字段都有值，屏幕类型清单写成具体的屏（"扫描进行中"），而不是抽象的概念（"用户体验"）。

## 2. 四圈

| 圈层 | 找什么 | 这一圈回答的问题 |
|---|---|---|
| **R1 直接竞品** | 同品类产品 | 行业惯例是什么？ |
| **R2 间接竞品** | 不同品类，但解决同一种用户需求或情绪 | 别人用什么方式满足同一个需求？ |
| **R3 结构相似** | 业务不同，信息结构或交互模型相似 | 同样的结构还有哪些解法？ |
| **R4 表达启发** | 任何品类里的视觉隐喻、数据可视化、状态动效、情绪表达 | 怎样表达得更好？ |

R1 是基准，R2–R4 是启发。R3、R4 的线索**优先从已保存的图中长出来**，起点名单只用来起步。R3、R4 的 App 不能是 R1、R2 里出现过的（构建会报错）。

起点名单：每圈列 3–10 个 App 或模式关键词，写进 `leads`（`from` 为 null）。示例（手机安全防护 App）：R1 Norton、Bitdefender；R2 1Password、NordVPN、Life360；R3 Oura 评分、Credit Karma、Ring 安防；R4 雷达扫描动效、圆环进度、盾牌隐喻。

## 3. 建网

在存放位置建立调研目录，里面有三样东西：

- `screens/`：截图，命名为 `{三位序号}_{圈层}_{App}_{屏幕类型}`，每张图存缩略图和大图两份，例如 `007_R1_Norton360_dashboard_thumb.jpg` 和 `007_R1_Norton360_dashboard.png`
- `research.json`：这张网的唯一事实来源，包括简报、模式、截图、线索、呼应、检查点和洞察。字段说明见 [`references/data-contract.md`](references/data-contract.md)
- `index.html` 和 `viewer/`：查看器，由构建脚本复制

每次写完 `research.json`，运行 `python3 scripts/build_web.py <调研目录>`。它会校验数据、生成查看器读取的 `research.js`，并把最新的查看器复制过去。

写完简报、第一次构建之后，**把调研之海打开给用户看**，让他看着网一点点长出来：在后台运行 `python3 -m http.server <端口> --directory <调研目录>`（端口任选一个空闲的，如 4310），再用当前环境的内置浏览器打开 `http://localhost:<端口>`；没有内置浏览器时，把这个地址告诉用户。页面每隔一两秒读取一次 `research.js`，每次构建后自动更新。内置浏览器打不开 `file://`，所以 Loop 期间用本地地址；调研结束后，双击 `index.html` 照样能看。

**页面门禁**：打开之后，用浏览器工具读取页面文字（或截图）确认：画面中央正在打出简报里的产品名，最后一行是 `WAITING FOR THE FIRST FRAME`（逐字打出要几秒，读到半截就稍等再读）。看到空白、报错，或"没有找到 research.js"，先修好再进入 Loop：确认服务还在运行、端口和目录对得上，然后刷新页面。用户必须从第一张图开始就看得到这片海。

如果目录已经存在，**先读取 `research.json`，从上次的位置继续**（断点续跑），不要从头开始。

**完成标准**：页面门禁通过；用 1 张图跑通"取图 → 存图 → 构建"整条链路，`build_web.py` 没有报错，页面上出现了这张图。如果不能导出图片文件，就改为存进 Mobbin Collection，并在 `gaps` 里写明原因。存放位置是 Google Drive 时注意：Drive 不能直接打开交互网页，需要同步到本地后再打开 `index.html`。

## 4. Loop

每一轮按顺序执行：

1. **选线索**：从 `leads` 中状态为 open 的线索里选一条。上一次构建输出的"建议"告诉你哪一圈缺得最多；有更值得追的线索时，跟着线索走。选定后更新 `now`（轮次、这条线索、一句话说你要做什么）并构建一次，用户在页面上能看到你正在追哪条线索。
2. **搜**：线索是 App 名时，先查到这个 App，再看它的屏幕和流程；线索是模式时，按画面写查询词，全局搜索。查询词的写法见 [`references/query-patterns.md`](references/query-patterns.md)，工具对照见 [`references/capabilities.md`](references/capabilities.md)。每次搜索在 `searches` 里记一条：查询词、来自哪条线索、**返回了几张**（`returned`）。
3. **看**：Mobbin 一次会返回很多张。把它们放在一起逐张看图片本身，而不是只看元数据，互相比较：哪几张真正说明了点什么？
4. **存**：**筛选门禁**：一次搜索留下的不超过返回的一半；一个 App 只留最有代表性的 3 张。两条都由构建检查，超了会报错。一张图要同时满足下面两条才留下：
   - 能写出一句具体的 insight（布局、信息层级、状态表达、文案、视觉隐喻、交互流程，任一方面都可以）
   - 和同一次搜索里的其他图、和已存的同一 App 的图相比，它是最好的那张

   保存后立即在 `screens` 里加一条记录，写清 `insight`（一句判断）和 `why_saved`（你当时的观察和判断，包括它比落选的图好在哪里；有多个观点时分行写，见 data-contract.md 的"笔记的排版习惯"），再把它的 id 写进这次搜索的 `saved`。图片会占用上下文，文字不会：**每存一张，就落一条文字**。
5. **呼应**：如果新图和某张已存的图在呼应或形成对照，写一条 `echoes`，用一句话说明两者的关系。
6. **扩散**：为每张保存的图写 0–2 条新线索，加入 `leads`，每条都写上理由。线索可以是：
   - 一个 App："这个评分面板像 Oura → 看 Oura"
   - 一个模式："风险等级用颜色加文字双重编码 → 搜 severity level"
   - 一种屏幕类型："权限引导做得好 → 搜 permission onboarding"
7. **构建并核对页面**：更新线索状态（open / done / empty），然后运行 `build_web.py`。脚本会输出配额和屏幕类型的差距、下一轮的建议，以及一行"核对"：页面左上角此刻应该显示的数字（如 `37 / 100 FRAMES`）。**页面门禁**：用浏览器工具读取页面，确认左上角的数字和"核对"一致（用户正在拖拽时会少几张，末尾的 `+N` 补齐）。两秒后还对不上，刷新页面；仍然不对，说明服务停了，重新启动它。这一轮在页面对上之后才算结束。

**每满 25%**：在 `checkpoints` 里写一条小结，回答三个问题：反复出现的模式有哪些？哪个圈层或屏幕类型不足？下一阶段往哪里扩散？前两个答案写进 `note`，第三个写进 `next`。同时整理 `patterns`，合并同义项，保持 5–8 个。查看器按模式决定截图在海上的方向和航道。写完**直接继续**下一轮。

**用户中途引导时**：Loop 进行中，用户随时可能在聊天里说话，比如"多找一些非安全类 App 的温和表达"。先用一句话回复你怎么理解、打算怎么做，然后把它变成 1–2 条线索写进 `leads`，标 `by: "designer"`，`reason` 写用户原话的要点；下一轮起优先追这些线索。如果引导改变了配额或屏幕类型，同步修改简报。回复完**直接继续** Loop，不停下来等确认。

**线索枯竭时**（连续 3 轮没有新增）：切换圈层，或者把查询词从产品名换成模式名（`dashboard score`、`scan progress`、`threat alert`）。

**工具出错时**：在 `gaps` 里记下错误原文，重试 1 次，再失败就跳过这条线索。App 在 Mobbin 上没有收录时，把线索状态标为 empty，然后换下一条。

**完成标准**：`build_web.py` 既没有错误也没有提醒，页面核对一致，才退出循环。没有错误意味着：每张图都来自一次留下不超过一半的搜索，没有 App 超过上限，R3、R4 没有 R1、R2 的 App；没有提醒意味着：数量达到 N，四个圈层都达到配额（±2 张），简报里每种屏幕类型至少 3 张，模式数量在 5–8 个。

## 5. 蒸馏

把整张网蒸馏成结论，写回 `research.json`，再构建一次。查看器就是交付物：

1. **模式**：给每个 `patterns` 补全 `common`（共性）、`forks`（分叉）和 `exceptions`（例外，以及它是亮点还是坑）。同时回答：R1 的惯例是什么，R2–R4 给出了哪些不同解法。
2. **洞察**：在 `insights` 里写 3–7 条可以直接用于设计决策的判断，`evidence` 中列出支撑它的图。写法见 [`references/synthesis.md`](references/synthesis.md)。
3. **精选**：在 `picks` 里列出最值得深挖的 10 张，每张写 2–3 句理由。
4. **缺口**：在 `gaps` 里写明哪些方向没有找到好的参考，下一轮怎么补。

如果调研对象是单个组件或流程，按 [`references/synthesis.md`](references/synthesis.md) 的八透镜深挖和原子模式来做，结论同样写回 `research.json`。

全部写完后，把 `now.done` 设为 true，再构建一次。页面会把网收起来，回到完整的布局。

**完成标准**：每条结论都能追溯到具体的图；一个没看过这些图的设计师，在查看器里读完概览就能做出设计决策。
