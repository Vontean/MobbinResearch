# Mobbin 调研工作流指南

> 本文件描述调研技能各步的判断准则。这些步骤依赖语义判断（理解用户意图、构造查询、提炼模式），不适合脚本化；可脚本化的部分见 `capabilities.md` 的"脚本"节，执行到对应环节时调用。

## 工作流总览

```
① 澄清组件 → ② 规划查询 → ③ 搜索与钻取 → ④ 看图提取 → ⑤ 提炼模式 → ⑥ 产出 HTML Spec → ⑦ 用户审阅
```

## ① 澄清要研究的组件

动手搜索前先确认三件事，缺一不可：

1. **组件/页面**：研究什么？登录页、设置页、onboarding、结账流程……
2. **平台**：iOS、Web（移动端还分 Android 吗？官方只有 ios/web 两档）
3. **调研目标**：用户要什么——找布局参考？学交互细节？对比竞品风格？决定后续分析深度

完成标准：能用一句话复述"研究 {平台} 的 {组件}，目标是 {目标}"，用户确认后进入下一步。

## ② 规划查询词

每个查询词遵循"具体描述元素与关系"原则，一次只问一件事：

- ✅ "login screen with email and password fields and social sign-in buttons"
- ✅ "onboarding with personalization steps and progress indicator"
- ❌ 否定词（"without ads"）、模糊风格词（"modern"）、不相关的关键词堆砌
- ❌ 把多个流程/组件塞进一个查询——拆开分别搜索

指定 App 钻取：在描述前加 App 名（"Notion settings screen with toggles"）。跨 App 对比时用同一组件描述换不同 App 名分别搜，或用纯组件描述做全局搜。

完成标准：每个查询词都能让不熟悉上下文的人明白"要找什么界面、含哪些元素、属于哪个 App（如有）"。

## ③ 搜索与钻取

按调研目标选择命令：

| 目标 | 命令 | 说明 |
|---|---|---|
| 单张界面参考 | `search_screens` | 默认 `mode=deep` 语义匹配；换角度搜索用 `exclude_screen_ids` 去重 |
| 多步流程 | `search_flows` | 返回整条流程按 position 排序的每屏预览 |
| 网站区块 | `search_sections` | Pricing/About/Footer 等 |
| 指定 App | 对应命令 + App 名查询词 | 钻取该 App 的屏幕或流程 |

轮次策略：先全局搜一轮建立候选集 → 针对 2-4 个代表性 App 各钻取一轮 → 结果不足时换角度（换元素词、换平台、换模式）再搜一轮。每轮记录"搜索词 + 来源链接"作为证据链。

完成标准：候选集覆盖"至少 3 个不同 App（全局搜时）或目标 App 的 3 个以上屏幕/1 条以上流程（钻取时）"，且有链接可溯源。

## ④ 看图提取

**必须逐张查看返回的图片本身**，禁止只凭元数据（app_name、标题）下结论。对重点屏幕用完整大图分析细节：

```bash
python3 scripts/fetch_screen_image.py https://mobbin.com/screens/<id> --out screens/
```

按四个维度观察每张屏幕：

1. **布局 Layout**：栏数、侧栏/内容区位置、卡片结构、间距节奏
2. **视觉层级 Visual hierarchy**：字号阶梯、颜色对比、留白、明暗主题
3. **交互 Interactions**：悬浮/按压态、按钮位置与文案、进度指示、空状态
4. **导航 Navigation**：Tab 结构、筛选方式、视图切换、返回路径

风格亮点（配色、圆角、动效、插画风格）单独记录。每张重点屏幕可附主色板：

```bash
python3 scripts/extract_palette.py screens/<id>.png --top 6
```

完成标准：每张纳入分析的屏幕都有"布局 / 层级 / 交互 / 导航"四维描述，重点屏幕附带大图与主色板证据。

## ⑤ 提炼设计模式

把 ④ 的观察跨 App 归纳，而不是罗列截图：

- **共性**：多个 App 都采用的做法（如"登录页普遍将社交登录置于邮箱表单上方"）→ 成熟模式
- **差异**：不同 App 的分叉点（如"设置页有的用分组列表、有的用卡片"）→ 可选项
- **例外**：与主流不同的做法，判断是亮点还是坑

每条模式注明来源 App 与链接。完成标准：每个维度（布局/层级/交互/导航/风格）至少有 1 条共性或 1 组差异，且每条可溯源。

## ⑥ 产出 HTML 设计 Spec

复制 `assets/spec-components.html` 的设计 token 与所需组件（重点图卡、参考墙、色板、模式卡；流程调研加步骤条；Lightbox 放页面末尾），替换占位符拼装单文件 HTML，供用户直接打开审阅。布局自由组合，不重写样式。结构：

1. 标题区：组件名 + 平台 + 调研日期 + 目标一句话
2. 图片收集：**重点图卡**（深挖屏幕，大图 + 四维分析 + 主色板；Mobbin 原站链接悬浮在图片右上角）+ **参考墙**（模式引用过的其余屏幕，缩略图，点击全屏查看）
3. 设计模式章节：⑤ 的归纳结果，用模式卡组件呈现，共性/差异/例外分节
4. 建议章节（可选）：基于模式给出该组件的推荐做法

所有图片引用本地 `screens/` 文件，HTML 与图片同目录，`file://` 直接打开即可查看。**交付前逐一核对 HTML 引用的每个图片路径在输出目录中都存在**（常见失误：只复制了 HTML 没复制图片目录，导致参考墙裂图）。

完成标准：用户打开 HTML 后，无需再打开 Mobbin 就能完整看到证据、分析与结论；每张重点图卡 hover 可出 Mobbin 链接；**每条模式卡引用的来源 App 都在图片收集中有对应图**（引用与证据一一对应，不允许出现"来源：App A vs App B"但图片收集中没有 App B 的情况）。

## ⑦ 用户审阅（可选后续）

将 HTML Spec 交给用户确认。用户明确要求实现时，才进入实现环节（按 ⑤ 的模式建议改造目标组件），否则停在审阅。
