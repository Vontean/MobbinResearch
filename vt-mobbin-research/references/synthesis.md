# 蒸馏：从参考图到设计判断

这份文档用于 SKILL.md 第 5 节。广度调研到这里，要把整张网收束成可以拿来做设计决策的结论。

## 八透镜

从"最值得深挖的 10 张"中挑出 3–5 张，逐一过下面八个透镜。每个透镜都要指向图上具体的 UI 证据：

1. **布局**：栏数、卡片结构、间距节奏
2. **视觉层级**：用户第一眼看到什么，最后看到什么；字号阶梯、对比度、留白
3. **交互**：按压态、按钮位置和文案、进度指示
4. **导航**：Tab 结构、筛选方式、返回路径
5. **信任**：界面如何降低用户的不确定和焦虑，例如安全提示、费用明细、确认清单、社会证明
6. **行动**：主 CTA 和次 CTA 分别是什么；破坏性操作如何在视觉上与其他操作分开；有几个操作在争抢注意力
7. **渐进披露**：哪些信息被收起来，等用户需要时才出现
8. **恢复**：用户出错、被阻断或想退回时，界面怎么接住他们

## 模式聚类

按 `pattern_tags` 归类，每个模式写清三件事：

- **共性**：多数 App 的做法，即成熟惯例
- **分叉**：不同 App 选择了不同的做法，这些是可选项
- **例外**：与主流不同的做法，判断它是亮点还是坑

**原子模式**：如果调研对象是组件或设计系统，就不按整屏归类，而是把屏幕拆成最小可复用的原子（如费率明细行、滑动确认、空状态插画）。每个原子记录四项：是什么 / 变体 / 在哪些 App 出现 / 为什么只在这个领域存在。

## Key Insight

Key Insight 是一句**判断**，而不是一句观察。写法：判断句 + 支撑它的图 id。

- 判断："在确认页重复金额、收款方和到账时间，可以降低用户确认前的焦虑"（#012 #031 #047）
- 观察："很多 App 在结账前显示金额"（这只是现象，还要继续追问它意味着什么）

判断的标准：没读全文的设计师可以直接拿来做决策。3–7 条为宜。如果只写得出 1–2 条，说明还需要深挖；如果超过 7 条，说明还没有蒸馏到位。

## 迁移纪律（用户要求把结论落地到自己的产品时）

从参考图中带走的是**结构**：步骤顺序、去除摩擦的手法、状态覆盖、信息优先级。留下的是**皮肤**：品牌色、插画风格、文案语气、对方的领域实体。

判断方法：假设换到一个完全不同的行业，这条做法还成立吗？成立，就是结构；不成立，就是皮肤。

把每条要落地的模式归入四个桶：

- **Keep**：直接沿用结构
- **Drop**：只属于对方领域的步骤，删掉
- **Adapt**：思路相同，细节换成本项目的组件、design token 和领域实体
- **Add**：本项目需要、但参考里没有的部分
